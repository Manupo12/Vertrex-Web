En `finance-workspace-screen.tsx`:

Divide el total de gastos por la **cantidad de transacciones**, no por la cantidad de meses. Si hay 50 transacciones en un mes, el runway se calcula como si fueran 50 meses.

## 4. Las fracturas ocultas (datos y lógica)

### A. `finance-service.ts` está arquitectónicamente roto
```tsx
"use server";

import { showToast } from "@/components/ui/toast-container";
// ...
export async function updateInvoice(...) {
  // ...
  showToast("Factura actualizada", "success");
}
```

`showToast` es una función de un **componente cliente** (`toast-container.tsx`) que muta estado React. Una Server Action corre en el servidor de Node.js, donde no hay árbol React ni DOM. Esto puede:
- Fallar silenciosamente.
- Causar error de hidratación.
- Simplemente no mostrar nada al usuario.

Además, este archivo actualiza facturas **sin auditoría** (`recordAuditEvent`), mientras que `workspace-service.ts::createWorkspaceInvoice` sí la tiene. ¿Cuál es el camino oficial?

### B. Cálculo de Runway matemáticamente incorrecto
En `finance-workspace-screen.tsx`:

```tsx
const averageMonthlyExpense = expenseTransactions.length > 0 
  ? totalExpenses / Math.max(1, expenseTransactions.length) 
  : 0;
const runwayMonths = averageMonthlyExpense > 0 ? netCash / averageMonthlyExpense : 0;
```

Divide el total de gastos por la **cantidad de transacciones**, no por la cantidad de meses transcurridos. Si en un mes hay 50 transacciones de gasto, el runway se calcula como si fueran 50 meses. El número es mentira.

### C. Campos financieros en tabla `clients` como fuente primaria
En `schema.ts`:
```sql
totalInvestmentCents: integer("total_investment_cents").notNull().default(0),
paidCents: integer("paid_cents").notNull().default(0),
pendingCents: integer("pending_cents").notNull().default(0),
```

Y en `workspace-service.ts`, `createWorkspaceClient` los setea manualmente. Pero también existen `transactions` e `invoices`. Si alguien crea una transacción directamente, el cliente no se actualiza. Esto genera desfase entre el "dinero del cliente" y el "ledger real".

### D. Mutaciones sin patrón unificado
- **Finance (invoices)**: `requestWorkspaceMutation({ kind: "invoice" })` → ¿a dónde va? No tengo el archivo de la API route, pero probablemente a un handler genérico.
- **Finance (schedules)**: `createBillingSchedule()` Server Action directa desde `billing-schedule-service` (no me pasaste este archivo, pero se usa en Finance).
- **Calendar**: `requestWorkspaceMutation({ kind: "event" })`.
- **Hub**: No muta nada inline, solo abre overlays.

Esto significa que si quieres agregar una nueva entidad, no sabes si hacer una Server Action, un API route, o un overlay.

## 6. Lo que está bien construido (no todo es malo)

- **El schema de DB**: Índices, enums, foreign keys, JSONB para metadata. Es profesional.
- **El snapshot pattern**: Leer todo en paralelo y mapear en memoria es eficiente para un OS interno.
- **El UI Store**: `useSyncExternalStore` con `open/close/toggle` es un patrón limpio y funciona bien.
- **Workspace Health**: La idea de calcular salud por módulo y mostrar indicadores en el sidebar es excelente.
- **Tipado**: Hay esfuerzo real de TypeScript en todo el stack.

## Diagnóstico final

El OS tiene **una base de datos y un shell sólidos**, pero la capa de aplicación (servicios y UI) fue construida por múltiples agentes sin un contrato común. El resultado es:

1. **Duplicación visual** (Finance repite secciones).
2. **Bypass arquitectónicos** (finance-service.ts evadiendo el God File pero rompiendo las reglas).
3. **Inconsistencia de UX** (inputs libres vs selects, modales inline gigantes).
4. **Schema sobre-ingenierado** con tablas huérfanas.
5. **Sidebar plano** sin respetar roles ni capacidades.
